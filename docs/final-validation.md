# Финальный прогон на B5

Используйте чистую Debian 13 amd64 в KVM на B5 и отдельный диск гостя. Для загрузки установщика и зависимостей гостю нужен HTTPS-доступ к GitHub и Debian. Запишите версию гостя, параметры VM, тег, коммит и SHA-256 архива. Проверьте отдельный путь управления физическим B5 до прогона и после снятия стенда.

1. Убедитесь, что каталог приложения и службы отсутствуют. Выполните обе команды из [README](../README.md#запуск-на-чистом-debian) в терминале. Сверьте установленную версию с последним релизом, а исполняемый файл API с проверенным архивом.
2. Проверьте доверенный HTTPS, вход и обязательную смену первичного пароля. Запишите контрольное значение в настройки стенда. Сохраните отпечаток сертификата, идентификатор загрузки, PID API и агента. Повторите установку. Проверьте PID, контрольную настройку и действующий сеанс.
3. Перезагрузите гостя. Проверьте новый идентификатор загрузки, автозапуск служб, HTTPS с прежним сертификатом, сохранность настройки и целостность SQLite.
4. Аварийно завершите основной процесс API, агента, монитора и sing-box по одному. Для каждого дождитесь нового PID и проверьте доступность API и сокета агента перед следующим отказом. Запишите длительность восстановления.
5. Проверьте ответ защищённого API без сеанса, отказ при запросе смены пароля с чужим Origin, атрибуты сеансовой cookie и права доступа к приватному ключу TLS и сокету агента.
6. Измерьте задержку HTTPS на новых соединениях и передачу TCP через два маршрутизируемых виртуальных сегмента с IPv4 и IPv6. Запишите число запросов, объём, медиану, 95-й процентиль и условия наблюдения. Скорость физических портов требует внешних узлов на LAN и WAN.

## Прогон r58 от 28 ноября 2026 года

На B5 развернули чистую Debian 13 amd64 в KVM с 2 vCPU, 1536 МиБ памяти и отдельным диском. Обе команды из README выполнили из терминала гостя. Тег установленного выпуска `v0.1.0-step50-20261128-1121-r58` соответствует коммиту `96c979c041d4cebe44e42976daabd8088ed48017`. SHA-256 архива совпал с опубликованным файлом суммы и digest GitHub. [Релиз r58](https://github.com/ASSever/debian-router-b5-2840/releases/tag/v0.1.0-step50-20261128-1121-r58)

```text
3ac75cb5b1d19f6423b6cfa6cf8b00c589309cdeab71eae6d9cbdf56454eab15
```

API слушал на `127.0.0.1:8081`. По доверенному HTTPS запрос Dashboard без сеанса получил 401, а с первичным паролем до его смены — 403. Смена пароля с чужим Origin получила 403, с разрешённым — 204. Старый сеанс после смены получил 401, вход с новым паролем прошёл. У сеансовой cookie проверены `Secure`, `HttpOnly`, `SameSite=Strict` и `Path=/`. Закрытый ключ TLS имел режим 0600, сокет агента — 0660. Пользователь вне группы агента получил отказ, член группы выполнил запрос состояния.

Чистую установку подтвердили в первом прогоне. После исправления проверочного сценария прогон повторили на новом диске. Загрузка зависимости GitHub один раз прервалась по тайм-ауту. Повтор команды завершил установку. Ещё один запуск установщика поверх работающего r58 сохранил PID API и агента, сертификат, сеанс и контрольную запись SQLite. После перезагрузки гостя изменился boot ID, все четыре службы запустились автоматически. Dashboard с прежним сеансом ответил 200 по доверенному HTTPS, контрольная запись сохранилась, `PRAGMA integrity_check` вернула `ok`.

После отправки `SIGKILL` основному процессу каждой службы измерили время до появления нового PID и успешной проверки служб, Dashboard, агента и SQLite.

| Служба | Время восстановления |
| --- | ---: |
| API | 2,61 с |
| Агент | 2,58 с |

Для HTTPS выполнили по 40 запросов к локальному `/healthz`, каждый с новым TLS-соединением и проверкой сертификата. Для TCP передали по 32 МиБ трижды для каждого семейства адресов через два маршрутизируемых veth-сегмента. Получатель проверил содержимое всех передач.

| Рабочий B5, r52 | 1,98 / 2,27 мс | 23 612,3 / 23 718,1 / 23 533,6 | 260,5 / 23 063,1 / 23 527,8 |

Первый замер IPv6 в обеих средах был заметно медленнее двух следующих. Результаты описывают передачу внутри ядра через виртуальные интерфейсы. Для измерения физических портов нужны внешние узлы.

Гость штатно выключен, временный диск удалён. После снятия стенда новый SSH-сеанс к рабочему B5 подтвердил обратный маршрут по Wi-Fi. SSH, networkd, API, агент и монитор активны, доверенный `/healthz` ответил 200.
